# SACRED PLANT SPIRIT HEALING
## Technical Specification — Version 1.1

**Project type:** Public website and event booking service  
**Interface language:** English  
**Hosting:** GitHub Pages  
**Backend:** Google Apps Script Web App  
**Database:** Google Sheets  
**Email:** Gmail / Google Apps Script MailApp  
**Administration:** Private web dashboard  
**Booking model:** Application → Manual Review → Approval → Deposit → Final Confirmation  
**Payments:** Deposit workflow; payment method and amount to be configured  
**Event capacity:** Limited, with waitlist support  
**Location:** To be confirmed by the organizer  
**Contact channels:** Email and Facebook Messenger

---

## 1. Project Objectives

Create an elegant, responsive English-language website for Sacred Plant Spirit Healing that allows visitors to:

1. Understand the ceremony and the organizer's approach.
2. Review preparation instructions and frequently asked questions.
3. Browse upcoming events and available dates.
4. Submit an application for a selected event.
5. Receive an application reference and status updates.
6. Receive deposit instructions after the organizer approves the application.
7. Contact the organizer through email or Facebook Messenger.

The organizer must be able to manage events, capacities, applications, deposits and booking statuses through a web-based administration interface without editing source code.

The website must not invent event dates, prices, locations, medical claims or legal permissions.

## 2. Technical Architecture

### 2.1. Frontend

**Technology:** HTML5, CSS3 and JavaScript, with React and TypeScript permitted if appropriate.

The frontend is deployed to GitHub Pages. It must support repository-based URLs and a custom domain if one is configured later.

Responsibilities:

- Render public pages and event listings.
- Validate application forms before submission.
- Display available dates and capacity status.
- Submit applications to the backend.
- Display application references and user-friendly error messages.
- Provide booking status instructions.
- Display the privacy policy and consent controls.

No privileged credentials may be embedded in frontend code.

### 2.2. Backend

**Google Apps Script Web App** provides the server-side application logic.

Responsibilities:

- Return published event data.
- Validate and process applications.
- Enforce capacity restrictions.
- Generate unique application references.
- Manage application statuses.
- Send email notifications.
- Process deposit-related status changes.
- Authorize administrative operations.
- Record administrative changes.

All sensitive operations must execute server-side.

### 2.3. Database

Google Sheets stores the application's structured data.

The spreadsheet must not be publicly accessible. Access is restricted to authorized administrators and the Apps Script execution identity.

Google Sheets is acceptable for an initial, relatively low-volume implementation. It does not provide the same transactional guarantees as a relational database. Therefore, all capacity-sensitive operations must use server-side locking and carefully controlled read/write sequences.

### 2.4. Email

Use Gmail through Google Apps Script, subject to account quotas and configuration.

Email delivery failure must not delete or invalidate a successfully stored application. Failed notifications must be recorded for retry.

## 4. Booking Workflow

The system must distinguish an application from a confirmed reservation.

### Stage 1 — Application

The visitor selects an available event and submits the application form.

The server validates the request and creates an application with status `PENDING_REVIEW`.

The application receives a unique reference, for example `SPH-XXXXXXXX`. The actual reference must be generated by the backend.

### Stage 2 — Manual Review

The organizer reviews the application in the administration dashboard.

Available actions:

- Approve.
- Decline.
- Add to waitlist.
- Request additional information.
- Cancel an application.

An approved application transitions to `AWAITING_DEPOSIT` if a deposit is required.

### Stage 3 — Deposit Instructions

After approval, the system sends deposit instructions through email.

The amount, currency, payment method, payment deadline and recipient details must come from organizer-configured settings.

No amount or payment details may be hardcoded as factual project data before they are provided.

### Stage 4 — Deposit Verification

For the first release, payment verification is manual.

The organizer checks the payment through the agreed payment channel and records the result in the dashboard.

A visitor's uploaded receipt or payment claim is not sufficient to mark a deposit as verified.

### Stage 5 — Booking Confirmation

After the deposit is verified, the organizer can confirm the booking.

The system changes the status to `CONFIRMED` and sends a confirmation email containing the event date, time, location instructions and preparation guide.

### Stage 6 — Waitlist

When an event is full, new applicants may join the waitlist if the organizer enables it.

A waitlisted application does not reserve a place. When capacity becomes available, the organizer may offer the place to an applicant.

### Booking Statuses

- `PENDING_REVIEW`
- `AWAITING_DEPOSIT`
- `DEPOSIT_REPORTED`
- `DEPOSIT_VERIFIED`
- `CONFIRMED`
- `WAITLISTED`
- `DECLINED`
- `CANCELLED`
- `EXPIRED`

All status transitions must be validated server-side. Only authorized administrators may verify deposits and confirm bookings.

## 5. Application Form

Required fields:

- Full name.
- Email address.
- Selected event.
- Number of requested places.
- Privacy consent.

Optional fields:

- Message to the organizer.
- Preferred contact channel, if needed.

Validation requirements:

- All mandatory fields must be completed.
- Email format must be validated.
- Requested places must be a positive integer within the event's configured limit.
- The event must be published, open for registration and not cancelled.
- Consent must be explicitly recorded.
- The same request must not create duplicate applications when a submission is retried.

The application form must not collect detailed medical histories or other sensitive information unnecessarily.

If eligibility screening is required, it must be handled through an appropriately protected process.

## 6. Capacity Management

Each event must have a configurable capacity.

The backend must calculate occupied places using the event's applicable reservation policy.

Recommended initial policy:

- `CONFIRMED` bookings count toward occupied capacity.
- Pending applications do not automatically count as confirmed places.
- The organizer may configure a temporary hold on places for approved applicants awaiting deposits.
- Any temporary hold must have an expiry time.
- Waitlisted applications do not occupy confirmed capacity.

A server-side lock must protect the critical capacity-check and booking operation.

The system must prevent concurrent requests from confirming more participants than the configured capacity.

For Google Sheets, the implementation must use `LockService` for critical operations and perform the final capacity check inside the locked operation.

If the backend cannot safely complete an operation, it must return a clear error and must not claim that a place has been reserved.

## 8. Administration Dashboard

The dashboard must be accessible through a web interface.

### 8.1. Authentication

Use Google identity and a server-side allowlist of authorized administrator email addresses.

Requirements:

- Only explicitly authorized accounts may access administrative functions.
- Each administrative request must be authorized server-side.
- An email address supplied by the browser must never be treated as proof of identity.
- If Google Apps Script cannot reliably verify the caller's identity under the chosen deployment configuration, use a separately authenticated administrative interface or a supported Google identity integration.
- Do not rely on a shared secret embedded in frontend JavaScript.

### 8.2. Dashboard Overview

Display:

- Upcoming events.
- Available places.
- Pending applications.
- Applications awaiting deposits.
- Deposits awaiting verification.
- Confirmed bookings.
- Waitlist count.
- Cancelled events.

- Publish or unpublish an event.

## 9. Email Notifications

Use branded HTML email with a plain-text alternative.

### Application Received

Subject: `We've received your ceremony application`

Explain that the application was received and is awaiting review. Include the application reference and selected event.

### Application Approved — Deposit Required

Subject: `Next steps for your ceremony application`

Include the event details, configured deposit amount and currency, approved payment instructions and deadline.

### Deposit Received — Verification Pending

Subject: `Your deposit is awaiting verification`

Confirm receipt of the applicant's payment report without falsely claiming that the funds have been verified.

### Booking Confirmed

Subject: `Your ceremony booking is confirmed`

Include the confirmed event date, local time, location instructions, preparation guide and contact details.

### Waitlist

Subject: `Your application is on the waiting list`

Explain that the applicant does not yet have a confirmed place.

### Declined or Cancelled

Provide a neutral explanation and appropriate contact instructions.

Email failure must be logged and recoverable. Sending a message is not proof that the recipient received or read it.

## 10. Deposit Handling

The first release does not implement automated payment processing.

Required functionality:

1. Configure a deposit amount and currency for each event.
2. Send payment instructions only after application approval.
3. Record a payment report.
4. Allow an authorized administrator to verify the deposit.
5. Record verification time and administrator identity.
6. Confirm the booking only after the configured conditions are satisfied.
7. Notify the applicant of the result.
8. Record cancellations and any refund-related administrative decisions.

The organizer must specify:

- Deposit amount.
- Currency.
- Accepted payment method.
- Payment recipient.
- Payment deadline.
- Cancellation and refund policy.

No real payment credentials, prices or payment links may be invented.

If an online payment gateway is introduced later, its integration must use the provider's secure server-side verification mechanism. A browser redirect or uploaded receipt alone must not mark a payment as paid.

## 11. Privacy and Security

Mandatory controls:

- HTTPS.
- Server-side input validation.
- Strict administrator authorization.
- Private Google Sheets access.
- Rate limiting or equivalent abuse controls.
- Spam protection.
- Safe output encoding.
- Protection against injection and cross-site scripting.
- No privileged secrets in the public repository.
- Restricted access to personal information.
- Retention and deletion rules.
- Privacy notice and explicit consent.
- Audit logging for sensitive operations.

The public interface must not expose spreadsheet identifiers or administrative endpoints beyond what is required for the application to function. Any publicly callable endpoint must treat all input as untrusted.

Before launch, verify applicable Philippine data protection requirements and the legal status of the actual activities and substances involved. Do not publish unsupported claims of legal authorization, medical approval or guaranteed safety.

## 16. Acceptance Criteria

The release is accepted only when:

- The website works on desktop and mobile.
- All public content is in English.
- Only published future events are displayed.
- Visitors can select a real configured event.
- Applications are stored and assigned unique references.
- Manual approval works correctly.
- Deposit instructions are sent only when appropriate.

- Booking confirmation follows the defined workflow.
- Event capacity cannot be exceeded through concurrent booking requests.

- The frontend deploys successfully through GitHub Pages.
- The backend can be maintained without exposing secrets.
