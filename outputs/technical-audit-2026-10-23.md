**Объём:** анализ исходников, Apps Script, конфигурации GitHub Pages, метаданных, статических медиа и доступности локальных сборочных инструментов. Изменения приложения не вносились; добавлен только этот отчёт.

## Итог

Текущая реализация **не соответствует ключевым требованиям проекта и не готова к безопасной публикации как авторитетного календаря мероприятий**. В коде остались автоматическая генерация фиктивных дат, запись и fallback на локальные демоданные, публикация событий по статусам, не подтверждающим их организатором, и обработчики регистрации/депозитов/статусов/администрирования. Фото и два MP3 есть в `docs/media`, но просмотренные исходники их не подключают. Сборка из исходников не подтверждена: локально отсутствуют Vite и TypeScript.

## Наиболее важные выводы

### P1 — блокирует приёмку: фиктивные события могут отображаться как реальные

- `src/data/initialData.ts` содержит `generateSaturdayEvents()`: функция вычисляет субботы с октября 2026 по декабрь 2028 и помечает их `AVAILABLE`.
- `src/services/api.ts` вызывает `initLocalStorage()`, сохраняет `INITIAL_EVENTS`, а при ошибке Apps Script или даже при успешном пустом ответе возвращает локальные события. Условие удалённой ветки требует `json.data.length > 0`; пустой список опубликованных мероприятий не считается достоверным результатом.
- `EventStatus` в `src/types/index.ts` не содержит отдельного состояния `CONFIRMED` или `DRAFT`. `apps-script/Events.gs` публично отдаёт `PUBLISHED`, `AVAILABLE`, `ALMOST_FULL` и `WAITLIST`, а новый Apps Script event по умолчанию получает `PUBLISHED`. В интерфейсе создания мероприятия начальный статус `AVAILABLE`.
- Следствие: посетителю могут показываться вычисленные, не внесённые организатором даты; событие, ещё не подтверждённое в нужном смысле, может пройти фильтр публикации.

**Требуемая коррекция:** удалить генератор, фиктивные начальные записи и localStorage fallback; задать однозначное серверное правило публикации, например `status === 'PUBLISHED'` после явного подтверждения организатором; пустой успешный ответ должен показывать «нет подтверждённых мероприятий», а сбой источника — отдельную ошибку, но не создавать и не показывать подменные даты.

### P1 — локальные имитации остаются в публичном приложении

- `src/services/api.ts` хранит ключи заявок, событий, платежей, настроек и audit в `localStorage`; там же находятся локальные функции создания заявок, изменения статусов и мероприятий, настройки и `resetDemoData()`.
- `src/components/AdminDashboard.tsx` использует эти локальные функции. В частности, сохранение мероприятия не направлено в Google Apps Script/Sheets.
- `src/main.tsx` предлагает при ошибке нажать Reload, но обработчик вызывает `localStorage.clear()`. Это удаляет **всё** локальное хранилище origin, а не только данные приложения; если хранилище недоступно, сама кнопка также может завершиться ошибкой.
- При сетевом сбое пользовательская заявка может получить локальный success-ответ, не попав в Google Sheets. Такой ответ не эквивалентен серверной записи.

**Требуемая коррекция:** исключить локальное хранение заявок, событий и статусов как рабочий backend; не использовать browser storage для имитации серверных данных. Не очищать все данные origin. Любые допустимые настройки интерфейса хранить отдельно от чувствительных записей и только если это действительно требуется.

### P1 — клиентский PIN не обеспечивает административную авторизацию

`src/components/AdminDashboard.tsx` содержит допускаемые строки `1234`, `katinawan` и `admin` в коде браузера. Это только UI-ограничение: опубликованный JavaScript доступен посетителю, поэтому PIN нельзя считать секретом или защитой серверных операций. Одновременно Apps Script содержит отдельные административные маршруты с `authorizeAdmin`; конфигурацию и режим развёртывания Apps Script по исходникам подтвердить нельзя. Фронтендовые административные функции сейчас в основном изменяют localStorage, а не Sheet.

**Требуемая коррекция:** удалить клиентскую админ-панель и связанный с ней тестовый PIN, если администрирование не входит в публичный продукт. Если оно нужно, выполнять каждую административную операцию только на доверенном backend с проверяемой авторизацией; не полагаться на скрытие элемента интерфейса.

### P1 — лишняя поверхность регистрации, платежей, статусов и администрирования

В `apps-script/Code.gs` сохранены публичный status lookup, приём заявок, report-deposit, обновление статуса, проверка депозита, сохранение мероприятий и изменение настроек. `apps-script/Payments.gs` реализует приём и верификацию депозитов; `apps-script/Applications.gs` содержит запись и административные переходы статусов. Аналогичные платёжные/status UI остаются в `src/components/StatusCheckModal.tsx`, а админ-операции — в `src/components/AdminDashboard.tsx` и `src/services/api.ts`.

Это не соответствует запросу на удаление ненужных Apps Script обработчиков. Удаление должно быть согласовано с бизнес-потоком: форма мероприятия, привязанная непосредственно к Google Sheet, может записывать строку без отдельного публичного Apps Script admin API; если нужен отдельный endpoint для создания события, он должен быть минимальным, явно предназначенным только для внесения/подтверждения мероприятия и защищённым серверной проверкой.

### P1 — интеграция с таблицей неоднозначна и не даёт надёжного статуса ошибок

- `src/data/initialData.ts` задаёт Apps Script URL как константу. `VITE_APPS_SCRIPT_URL` из `.env.example` исходниками не используется; пример настройки расходится с реальной конфигурацией.
- `fetchPublishedEvents()` при исключении Apps Script пишет предупреждение и возвращает локальные данные. Отдельного UI состояния «Google Sheets недоступна» нет.
- `submitApplication()` тоже при ошибке удалённой отправки записывает заявку только в `localStorage` и возвращает успех.
- Публичный Apps Script status lookup принимает reference и email, после совпадения возвращает имя и статус; ограничение частоты запросов в исходниках не видно. Публичные статусы/регистрация в целом относятся к операциям, которые проект просит убрать, но их наличие следует явно разрешить или удалить.

**Требуемая коррекция:** источник событий и результат его загрузки должны быть явными; запретить «успешное» локальное сохранение формы. Для любой оставляемой отправки обеспечить серверное подтверждение записи и сообщать пользователю об ошибке, если его нет. Сократить ответы публичных status endpoints до необходимого минимума и проверить защиту от перебора/частых запросов.

### P1 — галерея и аудио присутствуют в репозитории, но не подключены к приложению

- В `docs/media` находится 35 изображений, включая папку `gallery`, и два MP3: `Welcome to Katin-awan.mp3` и `bgm.mp3`.
- В `public` нет этих медиафайлов. По поиску в `src` не найдено ссылок на изображения галереи или MP3; просмотренные `Hero.tsx` и `CeremonySection.tsx` этих компонентов не содержат.
- В исходниках не обнаружены audio element/playback controls, последовательное воспроизведение Welcome → BGM, mute или управление громкостью.

**Требуемая коррекция:** определить единый источник медиа для публикации и сборки (например, каталог под `public/media`, если build/deploy pipeline копирует его в Pages); добавить явную галерею с корректными URL и доступными alt-текстами. Реализовать управление звуком, тихий начальный уровень и последовательное переключение треков. Учитывать, что браузеры могут отклонять автоматическое воспроизведение со звуком; при отказе `play()` интерфейс должен предложить пользователю включить звук жестом, а не показывать ложный статус воспроизведения.

### P1 — выкладка GitHub Pages не связана с обычной сборкой исходников

- `vite.config.ts` устанавливает `base: '/katinawan/'` для production — это согласуется с адресом проекта GitHub Pages.
- `docs/index.html` ссылается на `/katinawan/assets/...`, и соответствующие скомпилированные JS/CSS файлы находятся в `docs/assets`.
- `package.json` запускает обычный `vite build`, который по умолчанию собирает в `dist`; настройки `outDir` для `docs` нет.
- README предлагает GitHub Pages из ветки `main`, каталога `/docs`. Каталога `.github/workflows` нет; найденный `workflows-templates/ci.yml` лежит в шаблонах и сам по себе не является активным workflow.
- Следствие: успешная сборка в `dist` сама по себе не обновит контент, который GitHub Pages обслуживает из `docs`. Дальнейшая публикация исходников зависит от незафиксированного ручного шага или настройки вне репозитория.

**Требуемая коррекция:** выбрать и автоматизировать один путь публикации — активный workflow, который собирает и развёртывает Vite build, либо явную генерацию/обновление `docs`. В обеих схемах проверить, что медиа и базовый путь `/katinawan/` попадают в конечный артефакт.

### P1 — сборка и typecheck не прошли в текущем окружении

На машине Node `v26.5.1`, npm `11.17.0`, `node_modules` отсутствует, Bun не найден. Команды `npm.cmd run build` и `npm.cmd run lint` запускались, но остановились с `'vite' is not recognized` и `'tsc' is not recognized`. Установка зависимостей не выполнялась. Это **не доказывает ошибку исходников** — сборочные команды заблокированы отсутствующими зависимостями, поэтому успешная сборка и проверка типов остаются неподтверждёнными.

В корне есть `bun.lock`, но не `package-lock.json`; инструкции README используют `npm install`. Инструмент установки/CI следует унифицировать и зафиксировать lockfile, который реально используется выбранной командой.

### P2 — политика приватности обещает меры, которые исходники не доказывают

`PRIVACY.md` и `src/components/PrivacyModal.tsx` заявляют о частном Google Sheet, ограниченном доступе, HTTPS, правах субъектов данных и удержании данных только на необходимый срок. Из кода нельзя проверить фактические настройки sharing Google Sheet, права Script deployment, срок хранения/удаления данных и процессы исполнения запросов на доступ/исправление/удаление. Срок описан неконкретно. Поле сообщения/намерений относится к личной информации, при этом данные также могут идти через Google Forms/Apps Script. Из исходников нельзя подтвердить, какая именно внешняя форма сейчас собирает данные и как настроен связанный ответный Sheet.

`src/services/googleAuth.ts` запрашивает 13 Drive OAuth scopes, включая широкий `drive`, `drive.scripts` и несколько дополнительных write/read scopes; для сценариев списка, экспорта и создания папок это избыточная поверхность доступа. `firebase-applet-config.json` содержит клиентскую Firebase API key и OAuth client ID; такие идентификаторы в клиентском приложении сами по себе не следует принимать за серверные секреты, но проект Firebase/OAuth должен иметь ограничения доменов, API и scopes. Проверка фактических ограничений вне репозитория не проводилась.

В `apps-script/Code.gs` ответ об ошибке формируется из `err.toString()`. Стоит проверить, не раскрывают ли исключения внутренние детали пользователю, и возвращать наружу нейтральный код/сообщение, оставляя подробности в закрытом журнале.

### P2 — robots.txt и sitemap указывают на другой домен

В `public/robots.txt` sitemap указан как `https://katinawan.vercel.app/sitemap.xml`, а `public/sitemap.xml` содержит адреса `katinawan.vercel.app`. В README и запросе указан GitHub Pages `https://neuromicon.github.io/katinawan`. Даже если Pages сейчас работает из копии в `docs`, эти опубликованные метаданные настроены на другой домен и должны быть согласованы с фактически выбранным canonical URL.

## Рекомендуемый порядок исправлений

1. **Сначала закрыть риск неверной публикации:** убрать генератор дат, демоинициализацию и пустой/ошибочный fallback; оставить только подтверждённые будущие события из утверждённого источника.
2. **Сузить backend:** определить, какой канал остаётся для создания событий; удалить Apps Script регистрации, платежи, status и admin операции, которые не нужны целевому сценарию; проверить оставшийся endpoint и настройку его доступа.
3. **Удалить имитацию хранения и фиктивную админ-защиту:** убрать ключи localStorage и PIN; не выдавать receipt, пока сервер не подтвердил запись.
4. **Зафиксировать приватность:** сократить доступ OAuth, уточнить публичный ответ status endpoint, описать внешние обработчики и конкретные процессы хранения/удаления; отдельно подтвердить права Google Sheet и настройки Google Apps Script.
5. **Подключить галерею и два трека** с управлением громкостью/mute и отказоустойчивым пользовательским запуском аудио.
6. **Сделать build/deploy воспроизводимым:** выбрать lockfile/package manager, обеспечить workflow для Pages, собрать из зависимостей и проверить конечный `docs`/Pages артефакт; исправить robots/sitemap.

## Критерии приёмки

- Пустая таблица или ошибка Google endpoint никогда не порождает календарные даты или успешную локальную заявку.
- API и интерфейс показывают исключительно события с явно установленным подтверждённым статусом и будущей датой; непубличные и отменённые записи не возвращаются.
- В исходниках и браузерном runtime отсутствуют генератор суббот, fake initial events и localStorage-имитации заявок/событий/платежей; отсутствует вызов `localStorage.clear()`.
- В `apps-script/` остаются только необходимые для согласованного потока обработчики; нет публичных маршрутов регистрации, платежей, статусов или администрирования, если они признаны ненужными.
- Ни PIN/пароль, ни скрытие UI не используются как security boundary; оставшиеся операции имеют server-side auth.
- В опубликованном Pages артефакте доступны все 35 фото и оба MP3 по URL с базовым `/katinawan/`; галерея загружает изображения, музыка переключается Welcome → BGM, mute и громкость работают, а отказ автозапуска имеет ясный пользовательский fallback.
- Ошибка загрузки событий видна отдельно от состояния «нет подтверждённых мероприятий»; ошибка отправки формы не отображается как успех.
- `npm run lint` и `npm run build` проходят после чистой установки зафиксированных зависимостей; workflow реально находится в `.github/workflows` и выкладывает артефакт, который проверен по путям.
- `robots.txt`, sitemap и canonical/metadata используют фактический домен, и в репозитории/публичном bundle нет серверных credentials.
- Privacy notice соответствует реальным полям, внешним сервисам, доступам и процедуре/срокам удаления; настройки Google Sheet и Apps Script проверены отдельно у владельца сервисов.

## Ограничения ревизии

Не проверялись текущие Google Sheet permissions, настройки опубликованного Apps Script Web App, действующий статус CI в GitHub, фактическая загрузка live-сайта и браузерное поведение автозапуска. Сборка и typecheck не прошли из-за отсутствия локальных зависимостей. Это статический аудит содержимого доступной рабочей копии, а не проверка production backend или юридическое заключение.
